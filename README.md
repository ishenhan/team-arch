## 这是什么

一套"人 + AI"协作团队的开源架构。一人+多 AI、多人+多 AI 皆可，多个成员、多种平台（云 VM、云函数、本地机器、云电脑、纯云 API、独立 Agent），用同一套协议组队干活。

核心创新：**异构**——不同平台的 Agent 通过 castle（服务器）上的 lobby（大群）+ SPM 门铃协议协同，不局限于单一系统。

## 为什么用这个架构

这是一个现实需求：你可能会用到多家公司的 Agent，但它们无法互通。

各家公司开始推出自带云电脑的 Agent：每个 Agent 住在自己的云环境里，有自己的运行时、自己的通信方式。Agent 越来越多，越来越分散，但它们之间没法说话。

结果就是：人只能在中间当搬运工，手动把 A 的输出复制给 B。这不合理。

### 现有方案

目前让多个 AI 协作，主流做法有两种：

1. **Webhook 传信式**：消息从 poller → 文件 → worker → 本体，一层层往下传。每层都要处理内容：poller 的游标推进可能跳过同批消息，文件的 mv/rm 可能删掉新写入的行，worker 的 LLM 可能误判或编造。每多一层，就多一次出错的机会。
2. **单系统内置**：所有 Agent 跑在同一个平台里，用平台自带的通信机制。换个平台就得重写。

### 它们的问题

**Webhook 会丢消息**。内容每过一层就多一次丢失风险。传信式架构中，游标推进和文件操作都可能丢消息。

**单系统锁死平台**。Mac 上的 Agent 和云上的 Agent 没法组队，因为通信机制是平台绑定的。

**都没管分身问题**。AI 的记忆可复制，复制一份配置就是另一个实例。定时脚本调用 LLM 冒充本体发言时，群里出现两个相同的身份，系统无法区分，协作信任崩塌。现有方案对此没有规则。

**VM 定期重启丢东西**。Agent 都住在云 VM 里，平台定期整体替换 VM，只保留 home 目录。脚本、服务、系统配置说没就没，得靠重建脚本幂等恢复。记忆和状态管理全靠自己想办法。

### 我们的方案

**门铃代替传信**：哨兵只按铃不传内容（零 LLM，规则匹配），本体被叫醒后自己去拉实时消息。门铃不会丢，丢的是信。

**异构不锁平台**：Mac、云、服务器上的 Agent 用同一套协议，通过服务器大群协同。换平台只换接入方式，不换协议。

**身份用规则锁定**：群里只允许本体说话；定时任务禁止调用 LLM，只能唤醒；发言签名与 token 强制绑定，对不上就拒收。

**状态放外面**：消息存服务器，配置进 Git，记忆写文件。VM 重启了，拉起来接着干，不丢东西。

用这个架构的理由：**你的 Agent 们终于能直接对话了，你不用再当搬运工。**

## 5 分钟速览

- **一句话**：多平台 AI Agent，通过服务器大群 + 门铃协议，组成协作团队
- **SPM 收信**：Sentry（哨兵）→ Patrol（巡逻）→ Main（本体），哨兵只按铃不传内容
- **通信三件套**：🦉猫头鹰 POST 送信、🐕💨飞狗 GET 拍照取信、🔔铃铛只报有事
- **3 个协议**：SPM 收信 / 群聊发言 / GitHub 备份
- **6 种平台接入方案**：云 VM / 云函数 / 本地机器 / 云电脑 / 纯云 API / 独立 Agent
- **设计注记**：身份唯一性（AI 记忆可复制，靠规则定身份）/ AI 组织行为学 / 数字原住民
